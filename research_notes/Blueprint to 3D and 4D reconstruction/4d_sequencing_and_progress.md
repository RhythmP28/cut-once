# 4D: Build Sequencing, Assembly Understanding, and As-Built vs As-Planned Tracking (for "Cut Once", HTN 2026)

Scope note: "4D" here means the 3D model plus (a) an ordered/precedence-constrained build sequence and (b) a record of what has actually been built, updated as pieces are placed. Floor-plan-to-3D conversion and AR/headset delivery are out of scope (other researchers). GitHub metadata (stars, license, last push) was pulled via the GitHub API on 2026-09-18 unless noted.

## 1. 4D BIM: open-source tools linking a 3D model to a schedule, and automatic sequence generation

### Takeaway
The open-source 4D stack is real but desktop/Python-centric: IfcOpenShell's `sequence` API and Bonsai (ex-BlenderBIM) can attach IFC elements to tasks, dependencies, baselines and "actual" schedules and animate them, but no sequencing is automatic in those tools. Automatic sequence generation from BIM is a decades-old research area (rules, graph/topological sorts, structural-stability checks, and since 2025 LLMs). It is mostly unreleased code on proprietary data, so there is nothing to reuse in 36 hours beyond the data model.

### Cited Findings
**Open-source tools (mature, maintained):**
- IfcOpenShell (`IfcOpenShell/IfcOpenShell`): 2,793 stars, LGPL-3.0, pushed 2026-09-18 (active daily). Open-source IFC library and geometry engine — [GitHub](https://github.com/IfcOpenShell/IfcOpenShell)
- `ifcopenshell.api.sequence` provides a full scheduling data API. It includes `add_work_schedule` (PLANNED, BASELINE or ACTUAL types), `add_task`, `add_task_time`, `assign_product` (a product becomes a task output), `assign_sequence` (FS/FF/SS/SF dependencies), `assign_lag_time`, `cascade_schedule` (propagate date changes), `recalculate_schedule`, `create_baseline`, and calendars/recurrence. None of these functions generates a sequence automatically — [IfcOpenShell docs](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/sequence/index.html)
- Usage pattern: `ifcopenshell.api.sequence.add_work_schedule(model, name=...)`, `add_task(..., predefined_type="CONSTRUCTION")`, `assign_product(relating_product=wall, related_object=task)`. The guidance is to create IfcTask/IfcWorkSchedule/IfcRelSequence through the API, not raw `create_entity` — [search summary of IfcOpenShell docs/skills page](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/sequence/index.html); [community skill file](https://skills.lc/OpenAEC-Foundation/Computational-Design-Day-Delft-March-2026/openaec-foundation-computational-design-day-delft-march-2026-claude-skills-ifcopenshell-impl-ifcos-impl-sequence-skill-md)
- The IFC schema natively models "as-built" time. `IfcTaskTime` has ScheduleStart/ScheduleFinish, EarlyStart/LateFinish, TotalFloat, IsCritical, StatusTime, and **ActualStart** ("the date on which a task is actually started. It is a measured value"), **ActualFinish**, **RemainingTime**, and **Completion** ("extent of completion expressed as a ratio or percentage… a measured value"). The schema itself does no consistency checking between these values — [buildingSMART IFC4.3 source (IfcTaskTime.md)](https://github.com/buildingSMART/IFC4.3.x-development/blob/master/docs/schemas/resource/IfcDateTimeResource/Entities/IfcTaskTime.md)
- Bonsai (formerly BlenderBIM Add-on) is a free, open-source native-IFC authoring add-on for Blender built on IfcOpenShell. It "can create construction schedules, perform critical path analysis, and generate sequence animations" — [Blender Extensions / bonsaibim.org](https://bonsaibim.org/); [IfcOpenShell docs](https://docs.ifcopenshell.org/bonsai.html)
- Bonsai 4D work in progress, per an OSArch thread from Oct 2025 to Mar 2026: an interactive Gantt timeline with scrubbing, sequence animation, IfcTask/IfcWorkSchedule linking by GlobalId, and planned-vs-actual variance tracking. A contributor (Federico Eraso) proposed filtering, colour types (13 predefined construction types) and bulk "Copy 3D / Sync 3D" assignment. Only pieces have merged upstream (e.g., "automatic 3D element selection on task click", an element-count column), with the rest on an unmerged branch. **No automatic sequencing** is mentioned. Note: the fetched summary said "as of February 2025" for merges, but the thread spans Oct 2025–Mar 2026, so the date is likely Feb 2026 (unresolved) — [OSArch](https://community.osarch.org/discussion/3151/wip-proposal-for-advanced-interactive-4d-planning-features-in-bonsai-bim)
- xeokit SDK (`xeokit/xeokit-sdk`): 934 stars, AGPL-3.0, pushed 2026-09-08. A WebGL BIM/IFC viewer; no 4D/schedule example was found in its example index — [GitHub](https://github.com/xeokit/xeokit-sdk); [examples](https://xeokit.github.io/xeokit-sdk/examples/)
- A GitHub search for "4D BIM" returns almost nothing: a 2-star SSoLDAC-2022 challenge repo ("Integration of trajectory-based data into 4D BIM Semantic Digital Twin") and student Revit/Navisworks write-ups. No maintained open-source Unity or web 4D viewer was found — [GitHub search](https://github.com/SSoLDAC-2022/Challenge-3)
- Commercial 4D/XR tools exist. Synchro XR offers a 1:1-scale animated simulation of planned work on HoloLens 2 and lets users "track progress, comparing recently completed work directly with the model" — [AEC Magazine](https://aecmag.com/features/hololens-2-and-4d-construction/). NEXT-BIM lets users "select elements by highlighting them and instantly update their status", linking BIM elements to phases and statuses — [NEXT-BIM](https://next-bim.com/en/features/progress-tracking-tool/)

**Automatic sequence generation from BIM (research):**
- Kim, Park & Cho (KSCE J. Civil Eng., 24(11), 2020) automatically generate constructible **steel erection sequences** from BIM. They analyse node/connection relationships between steel elements and use "static indeterminacy variation" to check stability at each installation stage. Many random sequences are generated and turned into stable ones. The authors call it a foundational, **semi-automatic** step, with automated analysis/optimization left to future work — [UNLV repository](https://oasis.library.unlv.edu/fac_articles/779/); [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S1226798824018920)
- Related steel-sequence work uses an optimizer combining A* and a genetic algorithm with discrete action/status/interaction simulation in BIM — [ResearchGate](https://www.researchgate.net/publication/324706475_Automated_Generation_of_Optimal_Steel_Sequences_with_Discrete_Action_Status_and_Interaction_Simulation_in_BIM)
- Graph approach (AUC thesis, concrete skeleton): BIM-based search derives geometric and topological relationships per element type. DFS and **topological sorting** plus a GA/tabu-search hybrid then generate candidate construction sequences — [AUC Knowledge Fountain](https://fount.aucegypt.edu/etds/13/)
- Rule-reasoning approach (Tsinghua): constraint rules between components/activities infer logical order, and IFC-extracted quantities set durations, producing component-level schedules automatically — [Journal of Tsinghua Univ. (sciopen)](https://www.sciopen.com/article/10.16511/j.cnki.qhdxxb.2022.22.001)
- Case study on efficiently generating 4D BIM schedules (Nanterre 2 CESI project) — [Frontiers in Built Environment 2022](https://www.frontiersin.org/journals/built-environment/articles/10.3389/fbuil.2022.998309/full)
- LLM approach: CONSTRUCTA (Zhang & Yang, arXiv Feb 2025) uses LLMs with static RAG, context sampling and a "Construction DPO" preference-alignment step to automate schedules in semiconductor fab construction. It reports +42.3% on missing-value prediction, +79.1% on dependency analysis and +28.9% on automated planning over baselines, all on **proprietary** data. No code was mentioned — [arXiv 2502.12066](https://arxiv.org/abs/2502.12066)
- "4D BIM-Driven Framework for Automated Construction Progress Monitoring Using MCP-Enabled LLM" (ACM conference proceedings 2026) exists; only the title was seen, and its contents were not verified — [ACM DL](https://dl.acm.org/doi/10.1145/3795496.3795715)

### Inferences
- **What's automatic vs manual today:** in open-source tools, linking elements to tasks and animating them is well supported, but *authoring the sequence is manual* (or imported from a scheduler). Automatic sequencing exists only in papers and is domain-specific: steel stability, concrete topology, rule bases. LLM schedulers are the newest and least reproducible.
- The **IFC data model is the most reusable asset**. `IfcTask` (step) + `IfcRelSequence` (precedence) + `IfcRelAssignsToProduct` (which part the step installs) + `IfcTaskTime.ActualFinish/Completion` + PLANNED vs ACTUAL work schedules map one-to-one onto "build steps + what's actually been built". The team can mirror these names in its own JSON schema. They can also export a real IFC file via IfcOpenShell in Python on the server if they want a standards-compliance talking point.
- For a desk with fewer than 15 parts, a precedence DAG plus topological sort (the textbook version of the graph papers) is a few dozen lines of code, and any sequencing "research" beyond that is overkill.

### Gaps
- Could not verify whether Bonsai's full 4D branch (interactive timeline, variance tracking) is in a released Bonsai version as of Sept 2026; only partial merges were confirmed.
- Found no open-source Unity 4D BIM viewer, and no xeokit 4D example. This may exist in unindexed repos.
- CONSTRUCTA and the MCP-LLM 4D paper: no public code or data verified.

## 2. Assembly sequence planning and step-by-step instruction understanding (IKEA, LEGO)

### Takeaway
This area has the most public code and data. It includes datasets that align 3D parts, manual steps and real video (IKEA Manuals at Work, IKEA-ASM, IndustReal, HoloAssist), LEGO manual-to-plan and generation models (MEPNet, BrickGPT/LegoGPT, LTRON), and physics-based assembly-sequence planners (Assemble-Them-All, ASAP). All of them are research-grade Python/PyTorch pipelines. None is a drop-in "give me the build order for this desk" service. The strongest 2025–2026 VLMs still do poorly on fine-grained assembly understanding (e.g., roughly 38% on Flat-Pack Bench vs 94% for humans).

### Cited Findings
**IKEA furniture:**
- **IKEA Manuals at Work** (Liu et al., NeurIPS 2024 Datasets & Benchmarks; Stanford CogAI + J.P. Morgan AI Research) is the first dataset with "4D grounding of assembly instructions on Internet videos". It covers 36 furniture models in 6 categories (mostly chairs, tables, benches) and 98 Internet assembly videos with 34,441 annotated frames. Annotations include temporal step/substep alignment to manual steps, 2D–3D part correspondences, part segmentation, part 6D poses and camera parameters. Data is CC-BY-4.0 — [arXiv 2411.11409](https://arxiv.org/abs/2411.11409); [project page](https://yunongliu1.github.io/ikea-video-manual/); [NeurIPS](https://neurips.cc/virtual/2024/poster/97790)
- Repo `yunongLiu1/IKEA-Manuals-at-Work`: 68 stars, no license file detected by the GitHub API (README states CC-BY-4.0 for data), last push 2025-03-31. It ships an annotation interface, a pose-refinement UI, `render_part.py`, and a tutorial notebook — [GitHub](https://github.com/yunongLiu1/IKEA-Manuals-at-Work)
- Baseline results show how hard this is. Assembly-plan generation (predict a hierarchical assembly DAG from video): SingleStep 26.88% F1 (simple matching) / 2.72% (hard); GeoCluster 29.74% / 11.51%. Part-conditioned segmentation IoU: SAM-6D 0.16, CNOS 0.09. 6D pose: MegaPose and SAM-6D both struggle with occlusion and textureless parts — [arXiv HTML](https://arxiv.org/html/2411.11409v1)
- **IKEA-ASM** (Ben-Shabat et al., WACV 2021) is a "three million frame, multi-view" furniture assembly video dataset with depth, atomic actions, object segmentation and human pose. Code is MIT. Repo `IkeaASM/IKEA_ASM_Dataset` has 77 stars — [arXiv 2007.00394](https://arxiv.org/abs/2007.00394); [GitHub](https://github.com/IkeaASM/IKEA_ASM_Dataset)
- **IKEA-Manual: Seeing Shape Assembly Step by Step** (arXiv 2302.01881) is the predecessor manual-to-3D-step dataset. Its baselines score better than on video-derived plans — [arXiv](https://arxiv.org/pdf/2302.01881); [comparison in IKEA Manuals at Work](https://arxiv.org/html/2411.11409v1)
- **Manual2Skill** (RSS 2025) has a VLM read IKEA manual images and build a **hierarchical assembly graph** (parts, subassemblies, relations). It then estimates per-step 6D poses and plans robot motions, and assembled several real IKEA items. Repo `owensun2004/Manual2Skill`: Apache-2.0, 35 stars. A follow-up, **Manual2Skill++** (connector-aware), is at arXiv 2510.16344 — [arXiv 2502.10090](https://arxiv.org/abs/2502.10090); [project](https://owensun2004.github.io/Furniture-Assembly-Web/); [GitHub](https://github.com/owensun2004/Manual2Skill); [Manual2Skill++](https://arxiv.org/pdf/2510.16344)
- **IKEA-Bench** (arXiv 2604.00913, 2026): 1,623 questions over 6 task types on 29 IKEA products, evaluating 19 VLMs (2B–38B) under Visual / Visual+Text / Text-only instruction alignment — [arXiv](https://arxiv.org/html/2604.00913)
- **Flat-Pack Bench** (arXiv 2605.21625; listed under CVPR 2026 paper notes): 602 multiple-choice questions on IKEA assembly videos testing spatio-temporal understanding. "The strongest models, such as GPT-5, achieve only ~38% accuracy", vs 94.18% for humans — [arXiv](https://arxiv.org/pdf/2605.21625); [paper note](https://en.papernotes.org/CVPR2026/multimodal_vlm/flat-pack_bench_evaluating_spatio-temporal_understanding_in_large_vision-languag/)
- Also seen but not examined: FurnitureVLA (bimanual long-horizon furniture assembly, arXiv 2607.01212) and AssemblyBench (physics-aware industrial assembly, arXiv 2605.12845) — [FurnitureVLA](https://arxiv.org/pdf/2607.01212); [AssemblyBench](https://arxiv.org/pdf/2605.12845)

**LEGO:**
- **MEPNet** (Wang, Zhang, Mao, Cheng, Wu; ECCV 2022) translates a visual LEGO manual into a machine-executable plan. It reads manual images step by step, locates the components added to the current shape, and infers their 3D poses via 2D keypoint detection plus 2D–3D projection. Repo `Relento/lego_release`: MIT, 248 stars, last push 2022-08 (dormant) — [arXiv 2207.12572](https://arxiv.org/abs/2207.12572); [GitHub](https://github.com/Relento/lego_release)
- **BrickGPT / LegoGPT** (Pun, Deng, Liu, Ramanan, Liu, Zhu; CMU; ICCV 2025 Best Paper). It is an autoregressive LLM (fine-tuned Llama-3.2-1B-Instruct) that predicts the "next brick" from text prompts. A validity check and **physics-aware rollback** prune infeasible bricks, using a force-equilibrium stability model solved with Gurobi. Median generation time is 40.8 s, with a median of 2 rollbacks — [arXiv 2505.05469](https://arxiv.org/html/2505.05469v1); [project](https://avalovelace1.github.io/BrickGPT/)
- BrickGPT ordering caveat: bricks are generated in bottom-to-top raster order, which is **not** directly a buildable order. The authors apply an assembly-by-disassembly search to reorder bricks so each intermediate state is stable. Structures were assembled by humans and by dual Yaskawa GP4 robots — [arXiv HTML](https://arxiv.org/html/2505.05469v1)
- Repo `AvaLovelace1/BrickGPT`: MIT, 1,706 stars, last push 2026-05-21. Output is text ("hxw (x,y,z)" per brick), PNG, and LDraw. The dataset (StableText2Lego/StableText2Brick: 47k+ structures, 28k+ unique objects, 21 categories) is on Hugging Face — [GitHub](https://github.com/AvaLovelace1/BrickGPT)
- **Break and Make / LTRON** (Walsman et al., ECCV 2022) is an interactive LEGO simulator where an agent inspects and disassembles a model, then must rebuild it from scratch. Repos `aaronwalsman/ltron` (73 stars, last push 2024-07) and `ltron-torch-eccv22` — [arXiv 2207.13738](https://arxiv.org/abs/2207.13738); [GitHub](https://github.com/aaronwalsman/ltron)
- `intelligent-control-lab/StableLego` (MIT, 20 stars, pushed 2026-03) is from the same CMU group (Changliu Liu). It is a LEGO stability-analysis repo; its paper title and venue were **not verified** in this pass — [GitHub](https://github.com/intelligent-control-lab/StableLego)

**Physics/geometry assembly-sequence planning:**
- **Assemble Them All** (Tian et al., SIGGRAPH Asia 2022 / ACM TOG) plans physically plausible assembly motions and sequences by **assembly-by-disassembly** plus physics simulation. MIT, 219 stars, last push 2024-03 — [arXiv 2211.03977](https://arxiv.org/abs/2211.03977); [GitHub](https://github.com/yunshengtian/Assemble-Them-All)
- **ASAP** (ICRA 2024) does automated sequence planning for complex robotic assembly with physical feasibility. MIT, 106 stars, last push 2025-02 — [GitHub](https://github.com/yunshengtian/ASAP)
- Smaller ASP repos: `DLR-RM/GRACE` (graph assembly networks for sequence planning and feasibility learning, MIT, 13 stars), `labicon/ORASP-Code` (optimal robotic ASP as sequential decision-making, MIT, 11 stars), `wzl-muenker/AOG-Generation` (AND/OR graph generation, 8 stars) — [GRACE](https://github.com/DLR-RM/GRACE); [ORASP](https://github.com/labicon/ORASP-Code); [AOG](https://github.com/wzl-muenker/AOG-Generation)

**Procedural step and mistake datasets (useful for the "what goes next / did they do it right" framing):**
- **IndustReal** (Schoonbeek et al., WACV 2024): 84 egocentric videos of 27 participants assembling and maintaining a construction-toy car. It includes procedural errors (omissions) and execution errors, and defines tasks for **assembly state detection** and **procedure step recognition**. 3D models of all parts are public — [arXiv 2310.17323](https://arxiv.org/abs/2310.17323); [GitHub](https://github.com/TimSchoonbeek/IndustReal)
- **HoloAssist** (Microsoft, ICCV 2023): 166 hours from 350 instructor–performer pairs over 20 manipulation tasks, captured on **HoloLens 2** with 7 sensor streams. The instructor watches the performer's egocentric video live and guides by voice, which is close to a "voice copilot" setup. Mistakes are rare (~6% of fine-grained actions), which makes mistake detection hard — [arXiv 2309.17024](https://arxiv.org/abs/2309.17024)

### Inferences
- **Maturity:** datasets and benchmarks are mature and public. Generation and planning models (BrickGPT, Assemble-Them-All, ASAP) are solid research code but need GPUs, specific inputs (LDraw bricks, meshes with contact physics) and setup time. Manual/video understanding (MEPNet, IKEA Manuals at Work baselines) is still low-accuracy on real video.
- **Reusable ideas, not code:** (a) represent the plan as a hierarchical assembly DAG, as in IKEA-Manual, IKEA Manuals at Work and Manual2Skill; (b) "assembly-by-disassembly" to derive a feasible order: repeatedly remove a part that nothing else rests on, then reverse the list; (c) BrickGPT's "validity check + rollback" is conceptually the same as rejecting a placement whose prerequisites aren't met.
- For a desk, an LLM can propose an order from a part list (Manual2Skill shows VLMs can produce assembly graphs from manuals), but the team should review and freeze it. Evidence that VLM spatial reasoning is weak (Flat-Pack Bench, IKEA Manuals at Work baselines) argues against generating it live on stage.

- The IKEA-Bench per-model accuracy numbers were not extracted.

## 3. Progress monitoring: as-built vs as-planned (camera/point cloud vs BIM), accuracy, latency, on-device

### Takeaway
Two decades of research (Golparvar-Fard's D4AR onward) compare site photos or scans with a registered 4D BIM to label elements built/not-built. Accuracy is typically high in controlled settings (e.g., 97% material classification on patches, <6% MAE on activity completion). It needs careful registration, and it runs offline on photologs or point clouds, not in real time. Headset/phone real-time examples exist but are slow (HoloLens 2 at about 2 fps) or offload to a GPU PC. General VLMs (GPT-4V) recognise stages and materials but are weak at localization. Open-source code is thin: small academic repos and scan-to-BIM tools, no maintained "is element X built" library.

### Cited Findings
**Classic 4D-BIM + photo/point-cloud methods:**
- **D4AR** (Golparvar-Fard et al., ITcon 2009) is a 4D augmented-reality model for automating progress-monitoring data collection, processing and communication. It overlays site photos on the 4D BIM — [search result summary / ResearchGate](https://www.researchgate.net/publication/269047952_Automated_Monitoring_of_Operation-level_Construction_Progress_Using_4D_BIM_and_Daily_Site_Photologs); [US patent 9,070,216 "Four-dimensional augmented reality models for interactive visualization and automated construction progress monitoring"](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9070216)
- Han & Golparvar-Fard (2015) do appearance-based **material classification** on BIM-registered imagery from Structure-from-Motion point clouds for operation-level progress. They report **97.1% accuracy on 200×200-px patches**, but that patch size is too coarse for many elements — [ResearchGate](https://www.researchgate.net/publication/273834522_Appearance-based_material_classification_for_monitoring_of_operation-level_construction_progress_using_4D_BIM_and_site_photologs)
- Golparvar-Fard co-founded Reconstruct Inc., which commercialises this line of work (4D digital twins, progress from photos) — [Reconstruct blog](https://blog.reconstructinc.com/reconstruct-inc/what-ai-can-do-for-progress-monitoring-b47526fece5f); [Reconstruct 4D product](https://reconstructinc.com/product/4d-scheduling-4d-digital-twin)
- Most vision-based methods report **binary built/not-built** per element, which misses multi-stage progress. Newer work renders orthographic views of elements (projective transform or NeRF), segments them, and reports **activity-wise completion with <6% mean absolute error** — [Automation in Construction (ScienceDirect)](https://www.sciencedirect.com/science/article/abs/pii/S092658052300417X); [review summary](https://www.sciencedirect.com/science/article/pii/S2666165923001291)
- Other recent threads: drywall analysis for progress and QC (arXiv 2503.03422); material recognition with deep learning (arXiv 2006.16344); Mask R-CNN + BIM for indoor progress; multi-camera AI recognition pushed into BIM components (ISARC 2024) — [drywall](https://arxiv.org/pdf/2503.03422); [materials](https://arxiv.org/pdf/2006.16344); [indoor DL](https://www.sciencedirect.com/science/article/pii/S2666721524000346); [ISARC 2024](http://www.iaarc.org/publications/2024_proceedings_of_the_41st_isarc_lille_france/integration_of_construction_progress_monitoring_results_using_ai_image_recognition_from_multiple_cameras_onto_a_bim.html)
- **BIM-informed visual SLAM** (arXiv 2509.13972) associates detected walls with BIM walls as constraints in RGB-D SLAM to reduce drift. The motivation: on-site progress tracking and AR on portable devices need "real-time estimation and continuous updating of the as-built state" — [arXiv](https://arxiv.org/abs/2509.13972)

**Real-time / headset / phone:**
- An AR-based MEP progress-monitoring framework (2026, ScienceDirect "Results in Engineering"-style journal, ID S2590123026014143) trains on BIM-derived **synthetic data** and deploys the model on **HoloLens 2**. It shows as-built vs BIM discrepancies at **about 2 frames per second**. This comes from the search abstract only; the full text returned 403 — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S2590123026014143)
- **Augmented Assembly** (Kyaw [MIT], Ma, Zivkovic, Sabin [Cornell]; arXiv 2601.11535, TEI 2026) runs on HoloLens 2, with compute offloaded to an RTX 3060 workstation. YOLOv5 is trained on ~9k synthetic LEGO and ~16k synthetic 3D-printed-part images (mAP 0.876, F1 0.80). Steps are verified by hand–bounding-box intersection (96.2% correct-selection, 91.8% wrong-selection detection). LEGO task time was 12:39 with AR vs 25:54 with sorted parts and 32:11 unsorted. There was only a formative self-study, no FPS figure, and no code release found — [arXiv](https://arxiv.org/html/2601.11535); [ACM DL](https://dl.acm.org/doi/10.1145/3731459.3779354)
- "Augmented Reality and Vision-Language Models to Guide Humans Across Manual Tasks" (SIGGRAPH 2025 Immersive Pavilion): "each assembly step is validated using the VLM and a state-space encoding of all sub-assemblies", so user mistakes are detected and revert instructions given. Only the search abstract was available (full text 403); headset, latency and code were not verified — [ACM DL](https://dl.acm.org/doi/10.1145/3721245.3734043)
- **ASDF** (ISMAR 2024) does assembly state detection via late fusion with 6D pose estimation. Repo `roth-hex-lab/IEEE-ISMAR-2024-ASDF` (MIT, 0 stars) — [arXiv 2403.16400](https://arxiv.org/pdf/2403.16400); [GitHub](https://github.com/roth-hex-lab/IEEE-ISMAR-2024-ASDF)
- The State-Aware Configuration Detection for AR step-by-step tutorials (IEEE) notes that visual differences between assembly states "can be subtle" — [IEEE](https://ieeexplore.ieee.org/iel7/10316350/10316351/10316508.pdf)

**VLM / procedural "is this step done?" checks:**
- GPT-4V for construction progress (Ersoz, IPCMC 2024; arXiv 2412.16108) on aerial site imagery: "proficient in identifying construction stages, materials, and machinery" but "faces challenges with precise object localization and segmentation". No quantitative accuracy was reported — [arXiv](https://arxiv.org/abs/2412.16108)
- **STORM-PSR** (arXiv 2510.12385, accepted to CVIU) recognises correctly completed procedure steps in egocentric assembly video. An assembly-state-detection stream handles unoccluded views, and a spatio-temporal stream handles partial occlusion — [arXiv](https://arxiv.org/abs/2510.12385)
- **PROVIA** (arXiv 2609.20638, 17 Sep 2026) does online mistake detection by tracking procedure state (a Bayesian posterior over an automaton learned from correct demos). It runs at **58–70 FPS**, but recall is low at 0.1 false alarms/min: 15.4% on CaptainCook4D and 3.4% on HoloAssist. Code: `Kratos-Wen/PROVIA` — [arXiv](https://arxiv.org/abs/2609.20638)
- **Pro²Assist** (IMWUT 2026, arXiv 2605.04227) is a step-aware proactive assistant on AR glasses using MLLMs. It reports +21% procedural action understanding and 2.29× better proactive timing vs baselines; 90% of 20 users found it useful — [arXiv](https://arxiv.org/abs/2605.04227)
- PREGO / TI-PREGO do online mistake detection in procedural egocentric video, including LLM chain-of-thought / in-context learning to predict the next step. ProMQA-Assembly is a multimodal procedural QA dataset on assembly — [PREGO](https://arxiv.org/pdf/2404.01933); [TI-PREGO](https://arxiv.org/pdf/2411.02570); [ProMQA-Assembly](https://arxiv.org/pdf/2509.02949)

**Open-source repos (all small/academic):**
- `terrsoshi/construction-progress-monitoring-image-processing` (GPL-3.0, 10 stars), `jiashoujun/HDFT` (point-cloud feature tensor for fine progress, 3 stars), `sgh1998/CPMIP` (3 stars), `AminAzGol/indoor_construction_progress_monitoring_image_processing` (2 stars) — [GitHub search](https://github.com/terrsoshi/construction-progress-monitoring-image-processing); [HDFT](https://github.com/jiashoujun/HDFT)
- Scan-to-BIM tooling, which reconstructs BIM from scans rather than comparing against BIM: `LTTM/Scan-to-BIM` (BIM-Net++), `jingdao/Scan-to-BIM-Workshop` (Open3D), `mac999/scan_to_bim_pipeline`, the Cloud2BIM tool, and the BIMNet dataset (116.5M points, 25 scans with IFC) — [LTTM](https://github.com/LTTM/Scan-to-BIM); [BIMNet](https://thucbims.github.io/bimnet.thucbims.github.io/); [ISARC 2020 open-source Scan+BIM platform](https://www.iaarc.org/publications/fulltext/ISARC_2020_Paper_149.pdf)

### Inferences
- **Typical accuracy:** high (90%+) in constrained, well-registered, offline settings. It is much lower for fine-grained state changes in egocentric video (PROVIA recall is single to low double digits; Flat-Pack Bench top VLM is ~38%).
- **Typical latency:** offline, from minutes to daily for photolog/point-cloud pipelines. About 2 fps on HoloLens 2 for a purpose-trained detector. Real-time on a GPU PC for YOLO-style detectors and for PROVIA. A cloud VLM call on one frame is a request/response round trip (probably seconds, but **no source measured this** for this use case).
- On a known small object (a desk with distinct parts), the problem is much easier than site-scale monitoring. The system already knows *which* part should be next and *where*, so the check is a single binary question ("is the left leg attached?"). That is the best case for a VLM. Mistakes in state (wrong orientation, wrong hole) are the hard case the literature says VLMs miss.

### Gaps
- No measured latency or accuracy found for "send one headset frame + question to GPT-4o/GPT-5-class VLM → built/not-built" on furniture parts. The team would have to measure it themselves.
- Could not read the full text of the HoloLens 2 MEP paper or the SIGGRAPH 2025 AR+VLM paper (403). The numbers above come from abstracts/snippets.
- Did not find anything running as-built vs as-planned comparison natively on Quest 3 (out of scope for delivery, but noted).

## 4. Version history of physical builds ("git for physical assembly", digital-twin step tracking)

### Takeaway
There is no widely used "git for physical assembly" product. The closest real analogues are Git for IFC files (Bonsai's Git integration, which works because IFC-SPF is line-oriented and diffable) and Speckle (open-source, versioned AEC data with projects/models/versions). The IFC schema's PLANNED/BASELINE/ACTUAL schedules plus `ActualStart/ActualFinish/Completion` are the standards-based way to record "what actually happened when". An append-only event log of placements is the natural hackathon equivalent.

### Cited Findings
- Bonsai supports tracking an IFC project in a Git repository. Committing saves model state with a message, date and author. Tags label key revisions (e.g., TENDER, CONSTRUCTION, RevA) and appear as filterable prefixes in the revision list — [Bonsai docs: Tracking revisions with Git](https://docs-unstable.bonsaibim.org/guides/authoring/git_support.html)
- Why it works: "IFC-SPF is a line-oriented file format", and native-IFC apps (Bonsai, FreeCAD) serialise consistently, so an edited file differs only in the changed entities. Users run CI on push with `ifctester`/IDS rules — [OSArch: CI in IFC Git repositories](https://community.osarch.org/discussion/3175/continuous-integration-in-ifc-git-repositories-using-ids-and-validation)
- buildingSMART's IFC5 development discusses native-IFC and asynchronous (git-like) workflows — [IFC5-development issue #2](https://github.com/buildingSMART/IFC5-development/issues/2)
- Speckle is an open-source AEC data platform with Git-like versioning: Streams→Projects, Branches→Models, Commits→Versions. It tracks every change and supports compare/revert. "Everything core is open source" — [Speckle FAQ](https://speckle.guide/user/FAQs.html); [Medium: Speckle version control](https://jsdbroughton.medium.com/speckle-mastering-version-control-for-3d-aec-data-cb9e578b61a3); [Bricks & Bytes](https://bricks-bytes.com/technology/how-speckle-used-open-source-to-crack-aec/); [GitHub org](https://github.com/specklesystems)
- IfcOpenShell `add_work_schedule` supports PLANNED, BASELINE and ACTUAL types, and `create_baseline` snapshots a schedule for comparison — [IfcOpenShell docs](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/sequence/index.html)
- `IfcTaskTime.ActualStart`, `ActualFinish` and `Completion` are defined as measured values, and `StatusTime` is "the date or time at which the status of the tasks… is analyzed" — [buildingSMART IFC4.3 source](https://github.com/buildingSMART/IFC4.3.x-development/blob/master/docs/schemas/resource/IfcDateTimeResource/Entities/IfcTaskTime.md)
- Academic framing: "Towards integrated version control of virtual and physical artefacts in new product development: inspirations from software engineering and the digital twin paradigm" (Procedia CIRP 2021) argues physical and virtual artefacts and their iterations need joint version control — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S2212827121005953)
- Construction digital-twin writing treats the **as-built model** (including field changes) as the twin's foundation — [Archdesk blog](https://archdesk.com/blog/construction-digital-twin) (vendor blog, low authority)
- IFC and Bonsai stress that the schema does no consistency checks on task times, so applications must validate their own values — [IfcTaskTime](https://github.com/buildingSMART/IFC4.3.x-development/blob/master/docs/schemas/resource/IfcDateTimeResource/Entities/IfcTaskTime.md)

### Inferences
- "Version history that updates as real pieces are placed" = an **append-only event log** (event: part_id, new_state, timestamp, source = tap | vlm | voice, optional photo). Current state is a fold over events, and any past version is a replay to event *n*. That is git semantics (commits = events, HEAD = current state) without needing git.
- For a sponsor story, each event can also be written as a document to Elasticsearch, which the team already uses. Optionally, write an IFC with an ACTUAL work schedule where each placed part's task gets `ActualFinish` = placement time. That makes a credible "standards-compatible 4D" claim.
- "Branching" (what-if alternate orders) and "diff" (planned vs actual order) fall out naturally: compare the planned topological order with the actual event order.

### Gaps
- Found no open-source project that versions the *physical* state of an assembly from sensor data. The analogues version the digital model or schedule, not the camera-observed build.

## 5. Minecraft Litematica: schematic representation and the schematic verifier; real-world analogues

### Takeaway
Litematica stores a build as named regions of palette-indexed block states. Its verifier diffs "schematic world" vs "real world" block by block, sorting each position into CORRECT / WRONG_BLOCK / WRONG_STATE / MISSING / EXTRA, each with its own overlay colour and a HUD pointing to the nearest problems. Layer rendering and material lists give the "build it bottom-up" feel. This is exactly the as-planned vs as-built diff from construction research, only with a perfect sensor (the game knows every block). The Cut Once analogue is per-part states instead of per-voxel.

### Cited Findings
- Repos: `maruohon/litematica` (952 stars, LGPL-3.0, pushed 2026-07-26) and the actively maintained fork `sakura-ryoko/litematica` (886 stars, LGPL-3.0, pushed 2026-09-18) — [maruohon](https://github.com/maruohon/litematica); [sakura-ryoko](https://github.com/sakura-ryoko/litematica)
- Verifier result types: **CORRECT, WRONG_BLOCK** (different block type), **WRONG_STATE** (right block, wrong state such as orientation), **MISSING** (in schematic, absent in world), **EXTRA** (in world, not in schematic). "Each result type has an associated color" — [DeepWiki: Schematic Verification](https://deepwiki.com/maruohon/litematica/8.1-schematic-verification)
- Computation: `SchematicVerifierTask` runs asynchronously, **chunk by chunk**, comparing the schematic world with the client world. Results are stored as `BlockPairTypePosition` (expected state, found state, result type, position), with mismatches kept in multimaps (block-state pair → positions, e.g., `missingBlocksPositions`, `extraBlocksPositions`). DeepWiki does not confirm live incremental updates on block change — [DeepWiki (maruohon)](https://deepwiki.com/maruohon/litematica/8.1-schematic-verification); [DeepWiki (sakura-ryoko)](https://deepwiki.com/sakura-ryoko/litematica/8.1-schematic-verification-system)
- UI: `OverlayRenderer` draws coloured outlines, optional connecting lines between errors, translucent coloured sides, and a thicker outline on the looked-at block. An `InfoHud` panel shows mismatch type and expected vs found block when the player looks at a mismatch. Config keys include `VERIFIER_OVERLAY_RENDERING`, `VERIFIER_HIGHLIGHT_CONNECTIONS`, `VERIFIER_HIGHLIGHT_SIDES` and `VERIFIER_ERROR_HIGHLIGHT_ALPHA` — [DeepWiki](https://deepwiki.com/maruohon/litematica/8.1-schematic-verification)
- The verifier GUI lists all mismatches, the overlay highlights the selected ones in-world, and the HUD shows the locations of the closest problems — [CurseForge](https://www.curseforge.com/minecraft/mc-mods/litematica)
- Render Layers (config tab, hotkey M+C) switch modes and select which layer(s) of the schematic to show, which is how players build layer by layer. The Material List plus Material List HUD show what's needed, and a "Missing Chunks" message tracks unverified areas — [Litematica wiki FAQ](https://github.com/maruohon/litematica/wiki/Frequently-Asked-Questions); [Miraheze Mod Wiki](https://modwiki.miraheze.org/wiki/Litematica)
- Known edge case: wrong-state blocks were listed as "missing" in the material list — [issue #214](https://github.com/maruohon/litematica/issues/214)
- `.litematic` format (read from litemapy source): an NBT root with `Version`, `SubVersion`, `MinecraftDataVersion`, and `Metadata` (Name, Author, TimeCreated, EnclosingSize, TotalBlocks, TotalVolume). `Regions` holds a map of named regions, each with `Position`, `Size`, `BlockStatePalette`, `BlockStates`, `Entities`, `TileEntities` and pending ticks. `BlockStates` is a bit-packed long array with bits per entry = max(ceil(log2(palette size)), 2), indexed `y*W*L + z*W + x` — [litemapy schematic.py](https://github.com/SmylerMC/litemapy/blob/master/litemapy/schematic.py); [litemapy repo (GPL-3.0, 87 stars)](https://github.com/SmylerMC/litemapy)
- Ecosystem: `aleksilassila/litematica-printer` (AGPL-3.0, 348 stars) auto-places blocks from the schematic, the in-game "robot builder" analogue. `End-Tech/syncmatica` (CC0, 99 stars) shares schematics server-wide. `EndingCredits/litematic-viewer` (in-browser, deepslate renderer) and `albertchen857/Litematica-viewer` view them. `LucasDower/ObjToSchematic` (BSD-3, 523 stars) converts 3D models to .litematic/.schem — [printer](https://github.com/aleksilassila/litematica-printer); [syncmatica](https://github.com/End-Tech/syncmatica); [litematic-viewer](https://github.com/EndingCredits/litematic-viewer); [ObjToSchematic](https://github.com/LucasDower/ObjToSchematic)

**Real-world analogues:**
- Construction as-planned vs as-built (D4AR, scan-vs-BIM) is the same diff, but with noisy sensors and registration error instead of perfect block reads — [D4AR/Golparvar-Fard](https://www.researchgate.net/publication/269047952_Automated_Monitoring_of_Operation-level_Construction_Progress_Using_4D_BIM_and_Daily_Site_Photologs)
- Synchro XR on HoloLens 2 compares recently completed work against the 1:1 4D model, and NEXT-BIM does tap-to-update element status. Both are commercial versions of "verifier + layer mode" — [AEC Magazine](https://aecmag.com/features/hololens-2-and-4d-construction/); [NEXT-BIM](https://next-bim.com/en/features/progress-tracking-tool/)
- Augmented Assembly (HoloLens 2) shows a green check or red cross per step, a per-part CORRECT/WRONG signal — [arXiv 2601.11535](https://arxiv.org/html/2601.11535)

### Inferences
- The Litematica categories map directly to Cut Once part states: MISSING (ghost, not placed), CORRECT (placed and confirmed), WRONG_STATE (placed but flipped or rotated, which a VLM might flag), WRONG_BLOCK (wrong part used), EXTRA (rarely relevant for a desk). Litematica's "render layer" becomes "show only the current step's parts plus everything before". The material list becomes the cut list.
- Litematica's key advantage is ground truth for free: the game world *is* the sensor. In the real world the team must pick a source of truth: user tap, VLM, or tracking. That choice is the main design decision.

### Gaps
- Did not confirm from primary source code whether the verifier updates incrementally on block-change events or only on re-run. DeepWiki was silent, and source code was not read.

## 6. Most realistic path for the team in 36 hours

### Takeaway
Hand-author the build sequence as a small precedence DAG (IFC-style task/sequence/product names), make **tap/pinch/voice confirmation the source of truth**, and use a **constrained VLM photo check as an assistive "second opinion"** for the next expected part only. Store state as an append-only event log, which becomes the version history. Automatic sequencing and learned progress detection are high-risk research problems per the literature above and are not needed for a desk demo.

### Cited Findings
- Open-source 4D tools link elements to manually authored tasks and animate them. Sequencing is not automatic in Bonsai/IfcOpenShell — [OSArch](https://community.osarch.org/discussion/3151/wip-proposal-for-advanced-interactive-4d-planning-features-in-bonsai-bim); [IfcOpenShell sequence API](https://docs.ifcopenshell.org/autoapi/ifcopenshell/api/sequence/index.html)
- Automatic sequence research is semi-automatic, domain-specific, or on proprietary data — [Kim et al. 2020](https://oasis.library.unlv.edu/fac_articles/779/); [CONSTRUCTA](https://arxiv.org/abs/2502.12066)
- VLMs are weak at fine-grained assembly understanding and localization: GPT-5 ~38% on Flat-Pack Bench vs 94% for humans, and GPT-4V is poor at localization/segmentation in construction imagery — [Flat-Pack Bench](https://arxiv.org/pdf/2605.21625); [arXiv 2412.16108](https://arxiv.org/abs/2412.16108)
- Commercial tools use tap-to-update element status (NEXT-BIM). Research HMD systems use hand-tracking + detector checks at high accuracy (96.2%/91.8%) but need a trained detector and a GPU PC — [NEXT-BIM](https://next-bim.com/en/features/progress-tracking-tool/); [Augmented Assembly](https://arxiv.org/html/2601.11535)
- A 2025 AR+VLM system validates each step with a VLM plus a state-space encoding of valid sub-assemblies. This is the "VLM checks against a known set of valid states" pattern — [ACM DL (SIGGRAPH 2025)](https://dl.acm.org/doi/10.1145/3721245.3734043)
- Litematica's verifier model (MISSING/WRONG/EXTRA/CORRECT with colour overlay and nearest-problem HUD) is proven UX — [DeepWiki](https://deepwiki.com/maruohon/litematica/8.1-schematic-verification)
- The IFC schema already has fields for planned vs actual (PLANNED/ACTUAL schedules, ActualFinish, Completion) — [IfcTaskTime](https://github.com/buildingSMART/IFC4.3.x-development/blob/master/docs/schemas/resource/IfcDateTimeResource/Entities/IfcTaskTime.md)

### Inferences
**Recommended data model** (JSON on server, mirrored to Elasticsearch):
- `parts[]`: id, name, mesh/transform in desk frame, cut-list dims.
- `steps[]` (≈ IfcTask): id, title, `installs: [part_id]` (≈ IfcRelAssignsToProduct), `after: [step_id]` (≈ IfcRelSequence FS), `hint` (voice text), and an optional `reference_image` (render of the desk after this step).
- `events[]` (append-only, ≈ ACTUAL schedule): {t, part_id, state ∈ MISSING|PLACED|WRONG_STATE|WRONG_PART, source ∈ tap|voice|vlm, confidence, frame_ref}.
- Derived: current state per part (last event wins), "next" = steps whose `after` are all complete (topological frontier), progress % = completed/total. "Version n" = replay of the first n events. Diff = planned topological order vs actual event order.

**Sequencing:** hand-author 6–12 steps for the desk. If they want an "AI" touch, have the LLM propose steps and dependencies from the part list once (Manual2Skill-style assembly graph), then human-edit and freeze. Optionally add a one-line physics rule, "a part can be placed only if every part it rests on is placed" (the assembly-by-disassembly idea from Assemble-Them-All and BrickGPT), to validate the order.

**Confirmation, ranked by demo risk:**
1. Tap/pinch/voice "placed" as ground truth: zero ML risk, always works on stage.
2. VLM "second opinion": on confirm, or when the user asks "what goes next?", send the current headset frame plus a *narrow* structured prompt. The prompt names the expected next part, includes the step's reference render, and asks for JSON {part_id, status: placed|not_placed|wrong_orientation|unsure, reason}. Show the result as a suggestion ("Looks like the left leg is on — confirm?"), never as silent truth. Choose visually distinct parts (different colours or sizes) to maximise VLM reliability.
3. Automatic continuous detection (YOLO/pose tracking per part): skip. It needs training data, a GPU and registration. The HoloLens 2 examples reach about 2 fps or offload to a workstation.

**Nice-to-have export:** write an IFC via IfcOpenShell (`add_work_schedule(ACTUAL)`, `add_task`, `assign_product`, `assign_sequence`, task times with ActualFinish = event time) to say "our history is a standards-based 4D BIM". Git-commit each event's snapshot (Bonsai-style) if they want a literal "git log of the build".

### Gaps
- No source quantifies VLM round-trip latency or accuracy on single-part "is it attached" checks for furniture. The team should test this early (hour 1–3) on the actual desk parts and lighting.
- Did not evaluate which VLM (GPT-5-class vs smaller open models) is best on this narrow binary task; no benchmark found for exactly this setting.
